## 背景

`[update_check]`／`upd_url.json`（本家 `SysApp.ts:306`、分家 `UpdateCheck.ts`）は**これから配布するアプリ**しか救えない。
既に配布済みで、

- `update_check` 機構自体を持たない古いエンジンのアプリ
- 機構はあるがパッチサーバー自体が恒久的に死んでおり `upd_url.json` を仕込む手段もない（初回配布時にしか置けない）

というユーザーは、画面にエラーが出て終わり（`[update_check]自体のエラーメッセージ改善`は
engine側（bluesnovel／skynovel_esm）で対応済み・別件）。
これらを事後に救う唯一の手段として、**メーカーが別途配布する小さなパッチアプリ**（インストーラ本体をダウンロードさせるだけ）を
生成する新機能として検討する。本ドキュメントは設計メモ。

- **開発者** … 本家や分家のテンプレからオリジナルのゲームを製作する人（famibee以外を想定）。

## 課題：購入者チェック

パッチアプリをそのまま配布すると、未購入者でも新版インストーラをダウンロードできてしまう。
「旧版の本物を持っている」ことを確認してからダウンロードを許可したい。

## 前提の確認

bluesnovel／skynovel_esm 本体には暗号鍵の生成・管理ロジックが無い。`SysBase.decAB`
（本家も同型）は**プロジェクト側から注入される関数**で、鍵そのものはエンジンの外（sn_extension が
プロジェクトのビルド時に発行するファイル。TODO.md 本文の「プロジェクトの pass.json」）にある。

## チェック方式の選択肢

「購入者チェック」と「体験版誤認の回避」は別の課題として分けて考える。

### 主軸：購入者チェック（旧版の本物を持っているか）

#### 案A：インストール済みアプリの検出

- Windows: アンインストール情報（レジストリ）／既定インストール先の存在確認
- Mac: `/Applications/<AppName>.app` の存在確認
- 実装は軽いが、「アプリの存在」だけでは体験版インストールとも一致してしまう
  （→下記「体験版誤認の回避」で補う）。

#### 案B：暗号化アセットの復号可否チェック

- パッチアプリに鍵を埋め込み、旧アプリのインストールフォルダ内の暗号化済みアセット
  （1ファイルで十分）を実際に復号してみる。成功＝その鍵で暗号化された本物の資産を
  持っている、とみなす。
- パッチアプリ自身に鍵を埋め込む必要がある＝リバースエンジニアリングで鍵が抜かれる
  リスクを常に伴う。ただし本体の暗号化自体も「気休め程度」の位置づけ（要再確認）だと
  すれば、同水準のリスクとして許容できる可能性がある。
- crypto:false のプロジェクトでは使えない（そもそも暗号化されたアセットが無い）ので
  案Aとの併用が前提になる。

### 補助：体験版誤認の回避

案A・案Bのどちらも「アプリ／アセットの存在」しか見ておらず、体験版でも同じ結果になりうる。
これに対する具体策として、テンプレの `doc/prj/theme/setting.sn`（起動時に必ず読まれる
シナリオファイル）が使える：`&const.体験版 = false`（テンプレ標準の変数名）を持つので、
体験版と製品版とで**このファイルの中身（平文）が異なる**＝暗号化後のバイナリも異なるはず。

- crypto:false のプロジェクトなら平文のまま `体験版` 変数の値をテキストマッチするだけでよい。
- crypto:true の場合、二通りの実現方法がある：
  1. **鍵で復号してテキストマッチ**（案Bと同じく鍵埋め込みが要る）。
  2. **暗号化されたバイナリのままチェックサム比較**（鍵不要）：sn_extension がパッチアプリを
     生成する時点で「その製品版の `setting.sn` を暗号化した結果」のチェックサムを既知の値として
     パッチアプリに埋め込んでおき、旧アプリ側の暗号化済み `setting.sn` のチェックサムと突き合わせる
     だけで判定できる。**確認済み（`src/Encryptor.ts`）：暗号化は決定的。**
     AES-GCM を使うが IV はプロジェクトの `pass.json` に固定値として保存されており
     （毎回ランダム生成ではない）、鍵・IV・salt・iterations が同じプロジェクトの同じ平文は常に
     同じ暗号文になる。**鍵を一切パッチアプリに持たせずに済み、案Bの鍵漏洩リスクがまるごと
     無くなる**ため最有力。
- どちらの方式でも、変数名 `const.体験版` はテンプレ標準の慣習であり、プロジェクト側で改名・
  削除されていると検出できない（テンプレを使っている前提を置く）。
- 平文テキストマッチ・チェックサム比較のどちらも、ユーザーが手動でファイルを書き換えれば
  回避できる（＝本体の暗号化と同じ「気休め程度」の強度でよいと割り切るなら許容範囲）。

### 現実的な組み合わせ

案A（アプリ存在の検出）＋`setting.sn` 暗号化バイナリのチェックサム比較（体験版誤認回避、
鍵不要）の組み合わせが最有力：鍵をパッチアプリに一切持たせずに済み、案Bの鍵漏洩リスクを
避けながら購入者チェックと体験版判定の両方を満たせる。

✅ **判定ロジックだけ実装済み（2026-09-12）：[src/LegacyAppCheck.ts](../LegacyAppCheck.ts)
＋テスト [test/LegacyAppCheck.test.ts](../../test/LegacyAppCheck.test.ts)**
- `detectInstalledApp()` / `candidateInstallPaths()` … 案A。mac は
`/Applications/<name>.app`、win は `Program Files` 系の複数候補ディレクトリを見る
（レジストリは見ない）。判定対象と実行ホストの OS が一致する前提（本番はそう）
- `checksumHex()` / `matchesKnownChecksum()` / `encryptedChecksum()` … チェックサム比較。
`Encryptor` の決定的暗号化（既存実装）を利用するだけで、鍵は一切扱わない
- ⚠️ **まだどこからも呼ばれていない。** 未決の論点（`const.体験版` の固定・実装基盤・
配布経路）を先に詰めてから、パッチアプリ生成コマンドとして結線する

## 設計案（2026-09-12・コードは未着手。論点2・3への回答案）

### 実装基盤（論点2）【方針決定：Rust ＋ 自己参照データの末尾連結】

**`bun build --compile` は却下。** 実測したところ、クロスコンパイル自体は
（`bun build --compile --target=bun-windows-x64` で mac 上から win 向け exe を
生成できることを確認済み）問題ないが、**生成物が約82MB**（Bun ランタイム同梱のため）で、
Electron 最小構成（50〜150MB 程度）と同水準。論点2 の前提（Electron は重いので避けたい）を
そもそも満たせない。

**方針：Rust で「汎用バイナリ」と「プロジェクト固有データ」を分離し、配布時は連結して1ファイルにする。**

```
[Rust製 汎用バイナリ本体]  … 判定ロジック（案A＋チェックサム比較）。
                             全プロジェクト共通。ビルドは事前に1回（win/mac × x64/arm64 の組み合わせ分）
                                 +
[JSON: {appName, checksumSetting, downloadUrl}]  … プロジェクトごとに sn_extension が生成
                             upd_url.json と同程度の軽い処理（JSON化＋チェックサム計算のみ）
                                 +
[フッタ: JSONバイト長(u32 LE) ＋ 固定マジック文字列]  … 末尾8〜12バイト程度
                                 ↓ 単純にバイト列を連結するだけ（cat 相当）
[配布される1本の実行ファイル]
```

- **起動時の自己参照**：バイナリは `std::env::current_exe()` で自分自身のパスを取得し、
  ファイル末尾のマジック文字列で「データが付いているか」を確認 → その直前の u32 で
  JSON の長さを読む → 末尾からその長さ分シークして JSON を取り出す、という一般的な
  自己展開形式（NSIS 等の自己展開アーカイブと同じ考え方）
- **sn_extension 側がやるのはバイト列の連結だけ**（`Buffer.concat([stub, json, footer])`
  を書き出すだけの処理。`upd_url.json` 生成と同程度に軽い）。**Rust の判定ロジック自体は
  拡張機能側では書かない**（拡張機能側はビルド済みの汎用バイナリを持っているだけでよい）
- **判定ロジックは `LegacyAppCheck.ts` の Rust 移植**（案A・チェックサム比較。
  暗号鍵は一切埋め込まないので、移植によるリスク増は無い）
- Rust はビルドに時間がかかる（＝開発サイクルは重い）が、**ビルドは配布用バイナリの
  更新時だけ**でよく、プロジェクトごとの生成（実行頻度が高い方）はバイト列連結という
  軽い処理に閉じ込められる。**重い処理（コンパイル）と軽い処理（配布物生成）を
  分離できる**のがこの構成の利点

### 汎用バイナリの入手経路【決定：①同梱】

Rust バイナリ自体を **①拡張機能に同梱するか、②必要なときに GitHub からダウンロードするか**の
比較（下表）から、**①同梱に決定（2026-09-12・作者確認）**。

| | 利点 | 懸念 |
|---|---|---|
| **①拡張機能に同梱**（採用） | オフラインで完結。審査上の見た目もシンプル（同梱物として静的） | 使わない利用者にも vsix サイズが増える（win/mac × x64/arm64 で数バイナリ分。ただし Rust なら1本数MB規模なので、合計でも Electron 同梱よりは軽いはず。着手時に実測） |
| ②GitHub からDL（不採用） | 使う人だけがコストを払う。vsix は増えない | 「拡張機能が実行時に外部からバイナリを取得する」構図は、[build.md §5](build.md)の「VSIXの自動ダウンロード＆インストール機能を作らない」という既存方針に**似た形**になり、Marketplace 審査での見え方に懸念が残る |

理由：懸念の質が非対称（①は「サイズが増える」という定量的な問題、②は「審査観点で
疑われかねない」という定性的なリスク）で、再申請中の拡張機能としては**リスクを避ける方を選ぶ**。

### ダウンロードは既定ブラウザに委ねない【方針転換・2026-09-12】

**却下：既定ブラウザで download_url を開く案。** 購入者チェック（案A＋チェックサム比較）を
通過した「後」に URL をブラウザへ渡すと、アドレスバー・履歴に URL がそのまま残り、
**検証を経ていない第三者へその URL を転送・再配布できてしまう。** せっかくの購入者チェック
の意味が薄れる。

**採用：パッチアプリ自身が curl をサブプロセスで呼んでダウンロードし、完了後に自動的に
開く**（mac: `open <dmg>` で mount＋Finder表示まで、win: exe をそのまま起動）。
「機械が苦手な利用者でも exe/dmg→app をダブルクリックするだけ」レベルに寄せるための判断。

- HTTP クライアントクレートは追加しない。curl は mac 標準搭載・Windows 10 の 1803 以降で
  標準搭載なので、`dialog.rs` と同じ考え方（OS 標準ツールをサブプロセスで呼ぶだけ）で足りる。
  PATH 上の別の curl に化けないよう絶対パスで呼ぶ
- ⚠️ **トレードオフとして記録しておく：** ダウンローダーが直後に取得物を実行する
  パターンは、一般に AV のヒューリスティックにやや引っかかりやすい。ただし
  [build.md §5](build.md) の「自動ダウンロード＆インストールを作らない」は**拡張機能自身が
  別の拡張機能／VSIX を取得・導入する**話で脅威モデルが異なる（利用者の与り知らぬところで
  実行環境が書き換わる）。このツールは利用者が「更新を取得する」という単一目的のために
  自分の意思で起動するもので、実行主体の意図は起動した時点で既に確定している。
  本来の目的（正規購入者への更新配布）そのものであり、多くの正規アップデーターも同じ
  動作をするため許容する

### 配布経路（論点3・残り）

のみ。`upd_url.json` と同じ考え方で、**フォーマット自体を隠す必要はない**（安全性は
チェックサムの元になる暗号鍵の非公開性に依存し、鍵自体はバイナリにもデータにも含まれない）。
配布は各メーカーが自サイトで（ZIP化するかは任意）。ストア審査は絡まない。

「public GitHubのように一覧・検索されるのは避けたい／curl直リンクでのDLは維持したい」
という要件から検討し、**Cloudflare R2が第一候補**（egress無料・オブジェクトキー指定
のみで一覧機能自体が存在しない・S3互換APIのため乗り換えコストが低い）。さくらの
レンタルサーバー（`.htaccess`に`Options -Indexes`）も次点候補だが、R2側の技術検証が

✅ **R2アップロード・一覧・削除・公開URLでの実取得まで実機検証済み（2026-09-14）。**

  低レベルエラー）になる。Zero Trustの「View member ID」も別物で使えない。
  **確実な取得法：ダッシュボードのURL** `https://dash.cloudflare.com/<account_id>/...`
  の`dash.cloudflare.com/`直後の32文字がAccount ID（UIの見た目が変わっても崩れない）

  r2.devサブドメイン。本番向けではなく検証向けという位置づけは変わらない）

### 旧アプリ内の暗号化済み `setting.sn` の実際のパス特定【mac で調査・実証済み・2026-09-12】

**mac 実機（`/Applications/大阪九龍条.app`。本家エンジン・electron-builder 製）で調査完了。**

- **Electron アプリは `app.asar` に全リソースを1ファイルに固める。** パスは
  `<AppName>.app/Contents/Resources/app.asar`（`Info.plist` の `ElectronAsarIntegrity` で
  存在を確認できる。electron-builder の標準レイアウト）
- **ゲームアセットは asar 内の `out/renderer/prj/` 配下。** `theme/` フォルダに
  `setting.sn` 相当のファイルが **UUID 名**（拡張子は元のまま）で入っている
  （`@electron/asar list` で確認。`npx --yes @electron/asar` でインストール不要に一覧できる）
- ✅ **UUID の正体を実証済み：`uuidv5("theme/setting.sn", pass)` と完全一致。**
  実際のプロジェクト（`sn_kowloon`）の `pass.json` の `pass` 値を使って計算した結果が、
  asar 内の実ファイル名 `3b0bb3e8-deff-5722-94d5-885d9cb5fd0e.sn` と一致した。
  ロジックは [HDiff.ts:133](../HDiff.ts#L133) の `#REG_SPATH2HFN` 置換と同じ
  （`uuidv5(プロジェクト相対パス, pass)` ＋元の拡張子。`.sn` は対象外の変換なので拡張子維持）

**⚠️ 重要な帰結：このファイル名の算出には `pass`（本物の鍵）が要る。** パッチアプリには
鍵を一切持たせない方針（論点5）なので、**ファイル名の算出は sn_extension 側（生成時、
`pass.json` にアクセスできる開発者のマシン上）で行い、算出結果の文字列だけを設定JSONに
含める。** ファイル名自体は非秘匿情報（`upd_url.json` と同じ考え方）なので問題ない。

同じ理由で、**チェックサムを「パッチ専用の別鍵」で計算する案は成立しない。** チェックサム
比較は「実機に既に存在する、本物の鍵で暗号化されたファイル」のバイト列を確認する仕組み
なので、生成時の暗号化にも実機と同じ本物の鍵（＝そのプロジェクトの `pass.json`）を
使うしかない。AES-GCM は鍵が違えば同じ平文でも別の暗号文になるため、別鍵で作った
チェックサムは実機のファイルと絶対に一致しない。**安全性は損なわれない**：本物の鍵は
生成時にしか使われず、パッチアプリ・設定JSONのどちらにも渡らない（渡るのは
「導出済みファイル名」と「チェックサム値」という、鍵から一方向にしか作れない非秘匿情報だけ）。

⇒ **Config に `settingSnFileName` を追加**（例：`"3b0bb3e8-….sn"`。**basename のみ**、
asar内のフォルダ位置は問わない）。生成時に sn_extension が `pass.json` の `pass` から
`uuidv5()` で計算する。
- ✅ **フォルダ位置を問わない設計に変更（2026-09-13・ユーザー指摘）。** 当初案は
  `out/renderer/prj/` からの相対パス（`"theme/3b0bb3e8-….sn"`）を Config に持たせる想定
  だったが、**asar のヘッダ（ファイル一覧）を basename で探索すれば、フォルダ配置そのものを
  知らなくてよい。** UUID は `relPath+pass` から決定的に計算され、asar 内の実際の
  格納場所とは無関係に一意なので、`out/renderer/prj/` 配下のどこにあっても
  basename 一致で見つけられる。この探索はどのみち「asar内の1ファイル抽出」
  （下記）で asar ヘッダを読む処理の一部としてほぼ無償で実現できる
  → **残件6（本家／分家・エンジン世代をまたいだ asar 構成の一致性）は、この設定ファイル
  抽出という用途に限っては実質無関係になる**（他の用途で asar 構成に依存する処理が
  将来出てきた場合はその時点で別途検証が要る）

### asar 内の1ファイル抽出【実装済み・Rust 側・2026-09-13】

パッチアプリは 127MB 規模の asar 全体を読み込む必要はない。asar はヘッダ（JSON、
各ファイルのオフセット・サイズを記述）＋ファイル本体の連結という単純な形式なので、
**該当1ファイルの範囲だけシークして読めば済む。**

✅ **既存クレートに頼らず自前実装した：[patch_app/src/asar.rs](../../patch_app/src/asar.rs)。**
crates.io の `asar`（Absolucy/asar-rs、2年以上更新なし）は使わず、Chromium Pickle形式の
ヘッダを素の`serde_json`だけでパース。ファイルツリーを再帰的に basename 探索するだけの
小さな実装（依存追加なし）で足りたため、既存クレートの保守状況を心配する必要自体が無くなった。

✅ **実機の app.asar（127MB規模）で実地技術検証済み（2026-09-13）。**
`/Applications/大阪九龍条.app/Contents/Resources/app.asar` に対し `extract_by_basename()` を
実行し、既存ツール（`@electron/asar` の `extract-file`）で抽出した内容とバイト単位で一致
（3168バイト・sha256一致）することを確認した。所要時間は約18msで、127MBを読み込まず
該当ファイルだけシークして読む設計目標も実測で確認できた。
- **この検証中に、当初想定していたヘッダのバイナリレイアウトの誤りが見つかり修正した。**
  実際は `[4B: 外殻pickleのpayload_size(=4固定)][4B: header_size][4B: 内側pickleの
  payload_size][4B: JSON文字列長][JSON文字列]` という**二重の入れ子Pickle構造**で、
  当初コードは中間の1段（内側pickleのpayload_size）を数え忘れていた（合成テストの
  フィクスチャも同じ誤りを踏襲していたため、単体テストだけでは検出できなかった）。
  実機データで初めて発覚・修正し、単体テストのフィクスチャも実際のレイアウトに合わせて
  修正済み（4件・全パス）
- ✅ **Windows 版の asar パス（`asar_path_for_install()`。electron-builder の既定は
  `resources/app.asar`）も実機検証済み（2026-09-17）。** `sn_kowloon`（133MB規模）の
  `resources/app.asar` から `extract_by_basename()` で抽出し、`@electron/asar extract-file`
  の結果とバイト単位で一致（sha256一致）することを確認した。mac と同じ asar 構成で
  問題ないと判明したため、Windows のビルド成果物構成に関する懸念は解消
- `unpacked: true`（asar外に展開されたファイル）は**未対応**（`AsarError::Unpacked`を返す
  だけ）。`setting.sn` は小さいファイルで通常 unpack 対象にならない前提だが、万一の場合は
  未対応のまま失敗する

9. ✅ **archを一切見ていない → macOS 27 Golden Gate（Rosetta終了予定）を受けて
   「バージョン更新」とは別の「arch移行」を届ける必要が生じた → 対応実装済み
   （2026-09-17判明・同日実装）**

   **発端**：macOS 27 "Golden Gate"が2026-09-14にリリース済み。Apple Silicon専用の
   初バージョンで、Intel Macはこれ以上OSアップデートできない。Rosetta 2
   （Intelアプリをarm64上で動かす変換層）はmacOS 27までが一般アプリ向けの
   フルサポートで、**macOS 28（来年想定）で一般用途のRosettaは終了**し、以降は
   「古い保守されていないゲームタイトル」向けの限定サポートのみが残る見込み
   （SKYNovel製アプリがその対象に入るかは不明・Appleの基準が示されていない）。
   （[MacRumors](https://www.macrumors.com/2026/06/10/macos-golden-gate-last-to-support-intel-apps/)、
   [OSXDaily](https://osxdaily.com/2026/08/11/psa-macos-27-golden-gate-is-last-to-support-rosetta-intel-apps/)）

   **このツールへの影響**：過去にmac版をx64専用でビルド・配布していたメーカーの
   購入者が、Apple Silicon機でRosetta終了後のOSにアップデートすると、そのx64版が
   **起動できなくなる**。つまり本ツールには「新バージョンを配る」だけでなく
   「同じバージョンのままarm64／universalビルドに乗り換えさせる」という新しい
   役割が生まれた。

   **しかし現状の実装は、まさにこのケースで壊れる**：「既に最新版がインストール
   済みならDLをスキップする」判定（[patch_app/src/main.rs:86](../../patch_app/src/main.rs#L86)、
   `checksum_latest == installed_hash`）は、`setting.sn`の中身（または
   インストーラー本体のサンプル）から作るチェックサムの一致だけを見ており、
   **archの情報を一切見ていない**。開発者がバージョン番号を変えずにx64ビルドから
   arm64／universalビルドへ差し替えて再配布すると、`setting.sn`の中身は
   ビルドarchと無関係なので変わらず、`checksumLatest`は旧x64版と完全に一致する。
   結果、旧x64版の購入者に対して**「既にお使いのバージョンは最新です」と誤判定され、
   永遠にDLがスキップされ続ける**（arm64／universal版へ案内する道が無い）。

   [patch_app/src/detect.rs](../../patch_app/src/detect.rs)（インストール済みアプリ検出）も
   OS判定のみでarchを一切見ていない（macは`/Applications/{appName}.app`固定1パス、
   winは`ProgramFiles`系3ディレクトリを見るだけ）。

   **実装した対応（2026-09-17）**：
   - `patch_app`側に「インストール済みバイナリのarch判定」を追加
     （[detect.rs](../../patch_app/src/detect.rs)の`detect_installed_arch()`。
     Windows: PEヘッダのMachineフィールド、mac: Mach-Oヘッダのcputype／
     fat headerでuniversal判定。レジストリ等には依存せずファイルのバイト列のみで
     完結させる、このモジュール全体の方針を踏襲）
   - 設定JSONに`latestArch`（配布予定の最新版のarch。空文字列＝未提供）を追加
     （[footer.rs](../../patch_app/src/footer.rs)の`AppConfig::latest_arch`、
     TS側は[LegacyAppCheck.ts](../LegacyAppCheck.ts)の
     `T_LEGACY_PATCH_APP_CONFIG::latestArch`）。値は
     [genLegacyPatch.ts](../genLegacyPatch.ts)の`extractArchFromArtifactName()`が
     `latestInstaller`のファイル名（electron-builderの既定artifactName規約
     `${name}-${version}-${arch}.${ext}`）から抽出する。抽出できなければ空文字列のまま
     ＝archチェックを行わない従来動作にフォールバックする
   - スキップ判定を「`checksumLatest`が一致し、**かつ**archも一致する場合のみ
     スキップ」に変更（[main.rs](../../patch_app/src/main.rs)の`process_app()`）。
     ただしarch判定は自動検出（①setting.sn抽出）が成功した場合にしか行えない
     （②購入者にインストーラー本体を選ばせるフォールバック時は、インストール済み
     アプリ本体のパス自体が手に入らないため）。archが判定できない場合は
     従来通りスキップを許可する保守的な設計にした（後方互換：`latestArch`を
     渡さなければ挙動は変わらない）
   - Rust側3件・TS側1件のユニットテストを追加、`cargo test`（43件）・
     `bun test test/LegacyAppCheck.test.ts`（20件）・`bun run chk:types`で確認済み

   **再発防止策（別軸・検討のみ）**：mac側配布物（ゲーム本体・stub自体）を
   universal2ビルド（x86_64+arm64を1バイナリに）に寄せれば、今後は
   「archで悩まなくて済む」形にできる。ただしこれは**今後の**再発防止であり、
   **今まさに存在するx64専用の既存購入者を検知して案内する**という一回限りの
   移行問題そのものは、上記のスキップ判定改修が無いと解決しない。

   **副次論点（win側のarchも未整理）**：electron-builderの既定は
   `artifactName: '${name}-${version}-${arch}.${ext}'`（[PrjSetting.ts:307](../PrjSetting.ts#L307)）
   で、win-x64／win-ia32／mac-x64／mac-arm64の最大4種のビルド成果物が
   生まれ得る一方、GUI（`patch_gen_gui`）の「最新版インストーラー」欄は
   win/macの2つしか無くarch軸が無い。archの実行可否には非対称性がある
   （win: ia32バイナリはWOW64で64bit機でも動くが、x64はia32専用機で動かない。
   mac: x64バイナリはRosetta前提でarm64機でも当面動くが、arm64バイナリは
   Intel機で動かない）ため、「安全な代替arch」を選ぶならwinはia32側、macは
   x64側（Rosetta終了までの期間限定）が候補になる。ただし上記の通りmac側は
   Rosetta終了が迫っているため、恒久策としては勧められない。
