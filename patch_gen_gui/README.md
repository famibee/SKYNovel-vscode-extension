# パッチ生成ツール（試作単体アプリ・GUI）

過去アプリ向けパッチ配布物（購入者チェック付き。[../patch_app/](../patch_app/)）を、
GUIで作るためのツール。Tauri v2 ＋ プレーンHTML/JS製。

設計の経緯・判定ロジックの根拠は
[../src/docs/legacy-app-patch.md](../src/docs/legacy-app-patch.md) 参照。
このファイルは「作り方・使い方」だけを持つ。

**判定ロジックは一切持たない。** 画面で集めた入力から設定JSONを組み立てて、
[../src/genLegacyPatch.ts](../src/genLegacyPatch.ts)（実機データで検証済みの
生成CLI）を `bun` サブプロセスとして呼ぶだけの薄い作り。asar抽出・チェックサム
計算・downloadUrl検証等のロジックはRust側に再実装していない。

sn_extension（VSCode拡張機能）には組み込まない独立ツール。開発者（メーカー）が
手元で実行して配布物を作る。


## 事前準備

- **bun または node が入っていること**（本家か分家のゲーム開発環境があれば
  入っているはず）。GUIが `genLegacyPatch.ts` を `bun` コマンドで呼ぶ
- **stub（汎用バイナリ本体）をビルド済みであること**。[../patch_app/README.md](../patch_app/README.md)
  参照（`cd patch_app && cargo build --release`）


## 起動する

```sh
cd patch_gen_gui
cargo tauri dev      # 開発モード（コード変更を検知して再ビルド）
# または
cargo tauri build    # 配布用にビルド（src-tauri/target/release/ に生成）
```

このGUI自体は `sn_extension` リポジトリの中（`patch_gen_gui/`）から起動する前提
（`genLegacyPatch.ts` の在り処を相対パスで推測するため）。


## 画面の使い方

### 上部：共通設定

- **stub** — [patch_app](../patch_app/) でビルドした `sn_legacy_patch`
  （または `.exe`）を選択する
- **出力先** — 生成される配布物（1ファイル）の保存先を選ぶ

### アプリカード（「＋ アプリを追加」で複数追加できる）

1本の配布物に複数アプリ・複数バージョンをまとめられる。アプリごとに1枚
カードを追加する。

| 項目 | 内容 |
|---|---|
| appName | インストール済み判定に使うアプリ名。`genLegacyPatch.ts` の `appName` にそのまま渡る |
| pass.json | そのプロジェクトの `pass.json`（暗号鍵）を選択。鍵自体は配布物には一切含まれない |
| relPath | `setting.sn` の `doc/prj` からの相対パス（既定 `theme/setting.sn`） |
| crypto:true | プロジェクトの `crypto` 設定と合わせる |
| 実機にインストール済みの旧バージョンも自動スキャン | `scanInstalled`。同一OSの実機にそのアプリの旧バージョンがインストール済みなら自動で検出してチェックサムに加える（無くてもエラーにはしない） |
| downloadUrl | 新版インストーラの**直リンク**（`http(s)://` 必須。生成時に実際にHTTPリクエストして検証する） |
| 最新版インストーラー | 任意。選択（またはD&D）すると「アップロード」ボタンで下記R2にアップロードでき、返ってきた公開URLがそのまま`downloadUrl`欄に自動反映される。手入力で直リンクを持っている場合はこの欄は使わなくてよい |
| アップロード先ID | 最新版インストーラーのアップロード時にR2のURLパスへ使う**半角英数字**の識別子。appNameとは別枠（下記「アップロード先パスとappNameを分けた理由」参照）。プロジェクトフォルダ選択時は`package.json`の`name`から自動入力される |

### 過去インストーラー（mac / win）

過去に出荷したバージョンの**インストーラーファイルそのもの**
（`.dmg`／`.exe`）を追加する。平文の `setting.sn` を別途集める必要はない
——インストーラーから直接、暗号化済み `setting.sn` を抜き出してチェックサム化
する。

- ドラッグ&ドロップ、または「ファイルを選択…」ボタンで追加
- 一覧の各エントリの「削除」で取り除ける
- win欄・mac欄への分類は表示上の見分けやすさのためだけ（内部的には1つの
  配列にまとまり、拡張子で自動判別される）

過去出荷バージョンは、この「過去インストーラー」と上記の「実機スキャン」の
どちらか（または両方）で最低1件のチェックサムを確保できればよい。

### 生成する

すべて入力したら「配布パッチアプリを生成」を押す。下の実行ログに
`genLegacyPatch.ts` の標準出力・エラーがそのまま表示される。

### ホスティング管理タブ（Cloudflare R2）

配布物（最新版インストーラー等）をCloudflare R2にアップロード・一覧・削除できる。
個人利用の技術検証プロトタイプという前提で、入力値はこの端末のアプリ設定フォルダ
に平文で保存される（リポジトリには含まれない）。

- **Account ID** — Cloudflareダッシュボードの URL
  `https://dash.cloudflare.com/<account_id>/...` の `dash.cloudflare.com/` 直後の
  32桁の16進数文字列。メールアドレスではない
- **Bucket名** — R2バケット名
- **Access Key ID / Secret Access Key** — R2の Account API Token（Object Read & Write・
  バケットスコープ推奨）
- **公開ベースURL** — 任意。「パブリック開発URL」（旧称r2.devサブドメイン）または
  独自ドメイン。空欄だとS3 API用の認証必須エンドポイントがURLとして表示され、
  実際には機能しないため設定を推奨

保存後、「アップロード」欄から任意のファイルを直接アップロードできるほか、
上記アプリカードの「最新版インストーラー」からもワンクリックでアップロード
できる（保存先キーは自動的に `patch/<アップロード先ID>/<ランダムUUID>/<ファイル名>`
になる。ランダムUUIDを挟むのは、公開URLから他バージョン・他アプリのパスを
推測されないようにするため）。同じアップロード先ID配下の旧バージョンは
アップロード成功後に自動削除される。「アップロード済み一覧」は`patch/`配下のみ
（このツールが管理する範囲）を表示し、既存オブジェクトの確認・削除もできる。

#### アップロード先パスとappNameを分けた理由

`appName`は`/Applications/<name>.app`のようなインストール済みアプリの検出に
使う実名で、`productName`次第で日本語になりうる。これをR2アップロード先の
パスにそのまま使うと、配布パッチアプリ本体（`patch_app`）が`curl`サブプロセスの
引数として`downloadUrl`をそのまま渡す設計上、Windows環境の`curl.exe`で文字コード
起因の失敗リスクがある（実機で日本語パスのURLが実際に生成されることを確認して
判明）。そのため「アップロード先ID」を半角英数字限定の別項目として分離した。


## 制限・注意点

- **`downloadUrl` の検証に失敗しても生成は止まらない**（警告のみ）。一時的な
  ネットワーク障害の可能性があるため。配布前に手動でも確認すること
- **`crypto:true` の場合、過去インストーラーに体験版が紛れていないかは
  自動検証できない**（暗号化されていて中身を見られないため）。生成時に警告が
  表示されるので、渡すインストーラーが全て製品版であることは手元で確認する。
  `crypto:false` の場合は平文のままなので自動チェックされる
- **過去出荷ビルドの中には、体験版チェック機構（`&const.体験版`を持つ
  `setting.sn`）自体が実装されていない古いものがある**（テンプレート更新前の
  バージョン）。該当インストーラーを追加するとエラーになる。その場合は
  そのバージョンを一覧から外すこと（このパッチ配布の対象外）
- GUIのクリック操作自体の自動テストは無い（起動確認・実機データでの
  `bun`サブプロセス呼び出しはRust単体テストで検証済み）
