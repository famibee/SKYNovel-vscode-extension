## 背景

`[update_check]`／`upd_url.json`（本家 `SysApp.ts:306`、分家 `UpdateCheck.ts`）は**これから配布するアプリ**しか救えない。
既に配布済みで、

- `update_check` 機構自体を持たない古いエンジンのアプリ
- 機構はあるがパッチサーバー自体が恒久的に死んでおり `upd_url.json` を仕込む手段もない（初回配布時にしか置けない）

というユーザーは、画面にエラーが出て終わり（`[update_check]自体のエラーメッセージ改善`は
engine側（bluesnovel／skynovel_esm）で対応済み・別件）。
これらを事後に救う唯一の手段として、**メーカーが別途配布する小さなパッチアプリ**（インストーラ本体をダウンロードさせるだけ）を
生成する新機能として検討する。本ドキュメントは設計メモ。

### 登場人物・用語（2026-09-14 整理。TODO.md §0 より移動）

- **開発者** … 本家や分家のテンプレからオリジナルのゲームを製作する人（famibee以外を想定）。
  スクリプトは書けてもそこまでプログラミング知識がなく、GUI操作ぐらいはできる想定

「配布パッチアプリ」を**拡張機能の新機能として統合する部分**（内蔵GUI提供・購入者チェック
機構の本結線）は、引き続き Marketplace 再申請の返信待ち中は着手しない（TODO.md §1）。

## 課題：購入者チェック

パッチアプリをそのまま配布すると、未購入者でも新版インストーラをダウンロードできてしまう。
「旧版の本物を持っている」ことを確認してからダウンロードを許可したい。

## 前提の確認

bluesnovel／skynovel_esm 本体には暗号鍵の生成・管理ロジックが無い。`SysBase.decAB`
（本家も同型）は**プロジェクト側から注入される関数**で、鍵そのものはエンジンの外（sn_extension が
プロジェクトのビルド時に発行するファイル。TODO.md 本文の「プロジェクトの pass.json」）にある。

## 採用したチェック方式【2026-09-12決定】

「購入者チェック（旧版の本物を持っているか）」と「体験版誤認の回避」を分けて検討し、
以下の組み合わせを採用した。

- **購入者チェック＝インストール済みアプリの検出**。win: `Program Files`系の複数候補
  ディレクトリ、mac: `/Applications/<name>.app`の存在確認（レジストリは見ない）
- **体験版誤認の回避＝`setting.sn`の暗号化バイナリのままチェックサム比較（鍵不要）**。
  テンプレ標準の`doc/prj/theme/setting.sn`は`&const.体験版`の値を持ち、体験版・製品版で
  中身（暗号化後のバイナリも含む）が異なる。AES-GCMは同じ鍵・IV・平文なら常に同じ暗号文に
  なる決定的暗号化のため（`Encryptor.ts`で確認済み。IVは`pass.json`に固定値として保存され
  毎回ランダム生成ではない）、生成時に既知の製品版チェックサムをパッチアプリに埋め込んで
  おけば、**鍵を一切パッチアプリに持たせずに**判定できる
- **不採用：暗号化アセットを実際に復号して確認する方式**。パッチアプリ自身に鍵を
  埋め込む必要があり、リバースエンジニアリングでの鍵漏洩リスクを伴うため
- どちらの方式も`const.体験版`という変数名がテンプレ標準の慣習であることに依存し、
  ユーザーが手動でファイルを書き換えれば回避できる（本体の暗号化と同水準の
  「気休め程度」の強度と割り切る）

実装：[LegacyAppCheck.ts](../LegacyAppCheck.ts) ＋ テスト
[LegacyAppCheck.test.ts](../../test/LegacyAppCheck.test.ts)（`detectInstalledApp()`・
`checksumHex()`・`matchesKnownChecksum()`・`encryptedChecksum()`等）。

## 設計案（2026-09-12決定・論点2・3への回答案。実装済み）

### 実装基盤（論点2）【方針決定：Rust ＋ 自己参照データの末尾連結】

**`bun build --compile` は却下。** 実測したところ、クロスコンパイル自体は
（`bun build --compile --target=bun-windows-x64` で mac 上から win 向け exe を
生成できることを確認済み）問題ないが、**生成物が約82MB**（Bun ランタイム同梱のため）で、
Electron 最小構成（50〜150MB 程度）と同水準。論点2 の前提（Electron は重いので避けたい）を
そもそも満たせない。

**方針：Rust で「汎用バイナリ」と「プロジェクト固有データ」を分離し、配布時は連結して1ファイルにする。**

```
[Rust製 汎用バイナリ本体]  … 判定ロジック（案A＋チェックサム比較）。
                             全プロジェクト共通。ビルドは事前に1回（win/mac × x64/arm64 の組み合わせ分）
                                 +
[JSON: {appName, checksumSetting, downloadUrl}]  … プロジェクトごとに sn_extension が生成
                             upd_url.json と同程度の軽い処理（JSON化＋チェックサム計算のみ）
                                 +
[フッタ: JSONバイト長(u32 LE) ＋ 固定マジック文字列]  … 末尾8〜12バイト程度
                                 ↓ 単純にバイト列を連結するだけ（cat 相当）
[配布される1本の実行ファイル]
```

- **起動時の自己参照**：バイナリは `std::env::current_exe()` で自分自身のパスを取得し、
  ファイル末尾のマジック文字列で「データが付いているか」を確認 → その直前の u32 で
  JSON の長さを読む → 末尾からその長さ分シークして JSON を取り出す、という一般的な
  自己展開形式（NSIS 等の自己展開アーカイブと同じ考え方）
- **sn_extension 側がやるのはバイト列の連結だけ**（`Buffer.concat([stub, json, footer])`
  を書き出すだけの処理。`upd_url.json` 生成と同程度に軽い）。**Rust の判定ロジック自体は
  拡張機能側では書かない**（拡張機能側はビルド済みの汎用バイナリを持っているだけでよい）
- **判定ロジックは `LegacyAppCheck.ts` の Rust 移植**（案A・チェックサム比較。
  暗号鍵は一切埋め込まないので、移植によるリスク増は無い）
- Rust はビルドに時間がかかる（＝開発サイクルは重い）が、**ビルドは配布用バイナリの
  更新時だけ**でよく、プロジェクトごとの生成（実行頻度が高い方）はバイト列連結という
  軽い処理に閉じ込められる。**重い処理（コンパイル）と軽い処理（配布物生成）を
  分離できる**のがこの構成の利点

### 汎用バイナリの入手経路【決定：①同梱】

Rust バイナリ自体を **①拡張機能に同梱するか、②必要なときに GitHub からダウンロードするか**の
比較（下表）から、**①同梱に決定（2026-09-12・作者確認）**。

| | 利点 | 懸念 |
|---|---|---|
| **①拡張機能に同梱**（採用） | オフラインで完結。審査上の見た目もシンプル（同梱物として静的） | 使わない利用者にも vsix サイズが増える（win/mac × x64/arm64 で数バイナリ分。ただし Rust なら1本数MB規模なので、合計でも Electron 同梱よりは軽いはず。着手時に実測） |
| ②GitHub からDL（不採用） | 使う人だけがコストを払う。vsix は増えない | 「拡張機能が実行時に外部からバイナリを取得する」構図は、[build.md §5](build.md)の「VSIXの自動ダウンロード＆インストール機能を作らない」という既存方針に**似た形**になり、Marketplace 審査での見え方に懸念が残る |

理由：懸念の質が非対称（①は「サイズが増える」という定量的な問題、②は「審査観点で
疑われかねない」という定性的なリスク）で、再申請中の拡張機能としては**リスクを避ける方を選ぶ**。

### ダウンロードは既定ブラウザに委ねない【方針転換・2026-09-12】

**却下：既定ブラウザで download_url を開く案。** 購入者チェック（案A＋チェックサム比較）を
通過した「後」に URL をブラウザへ渡すと、アドレスバー・履歴に URL がそのまま残り、
**検証を経ていない第三者へその URL を転送・再配布できてしまう。** せっかくの購入者チェック
の意味が薄れる。

**採用：パッチアプリ自身が curl をサブプロセスで呼んでダウンロードし、完了後に自動的に
開く**（mac: `open <dmg>` で mount＋Finder表示まで、win: exe をそのまま起動）。
「機械が苦手な利用者でも exe/dmg→app をダブルクリックするだけ」レベルに寄せるための判断。

- HTTP クライアントクレートは追加しない。curl は mac 標準搭載・Windows 10 の 1803 以降で
  標準搭載なので、`dialog.rs` と同じ考え方（OS 標準ツールをサブプロセスで呼ぶだけ）で足りる。
  PATH 上の別の curl に化けないよう絶対パスで呼ぶ
- ⚠️ **トレードオフとして記録しておく：** ダウンローダーが直後に取得物を実行する
  パターンは、一般に AV のヒューリスティックにやや引っかかりやすい。ただし
  [build.md §5](build.md) の「自動ダウンロード＆インストールを作らない」は**拡張機能自身が
  別の拡張機能／VSIX を取得・導入する**話で脅威モデルが異なる（利用者の与り知らぬところで
  実行環境が書き換わる）。このツールは利用者が「更新を取得する」という単一目的のために
  自分の意思で起動するもので、実行主体の意図は起動した時点で既に確定している。
  本来の目的（正規購入者への更新配布）そのものであり、多くの正規アップデーターも同じ
  動作をするため許容する

4. 「アップロード済み一覧」は`patch/`配下限定表示（バケット共用時の誤操作防止）

### 旧アプリ内の `setting.sn` の実際のパス特定【mac実機・2026-09-12実証済み】

Electronアプリは`app.asar`（mac: `<App>.app/Contents/Resources/app.asar`、
win: `resources/app.asar`）に全リソースを1ファイルに固める。ゲームアセットはasar内の
`out/renderer/prj/`配下（本家分家・エンジン世代によって配置は異なりうるが、下記
basename探索方式のため無関係）にあり、`setting.sn`相当のファイルは**UUID名**
（`uuidv5(相対パス, pass)`＋元の拡張子。[HDiff.ts:133](../HDiff.ts#L133)の
`#REG_SPATH2HFN`置換と同じロジック）で格納されている。実際のプロジェクト
（`sn_kowloon`）の`pass.json`で計算した結果が、asar内の実ファイル名と完全一致する
ことを実証済み。

**重要な帰結**：ファイル名の算出には`pass`（本物の鍵）が要るため、**算出は生成時
（sn_extension側、pass.jsonにアクセスできる開発者のマシン上）で行い**、算出結果の
文字列（`settingSnFileName`。basenameのみ）だけを設定JSONに含める。同じ理由で
チェックサムを「パッチ専用の別鍵」で計算する案も成立しない（実機の本物の鍵で
暗号化されたファイルと一致させるには、生成時も同じ本物の鍵を使うしかない）。
ファイル名・チェックサム値はどちらも鍵から一方向にしか作れない非秘匿情報なので、
安全性は損なわれない。

**basenameのみで探索する設計**（asarのヘッダをbasenameで探索すれば、フォルダ配置
そのものを知らなくてよい）にしたため、本家／分家・エンジン世代をまたいだasar内の
フォルダ構成の違い（実際に`out/renderer/prj/`と`doc/crypto_prj/`という異なる配置を
確認済み）は、この設定ファイル抽出という用途に限っては無関係になった。

### asar 内の1ファイル抽出【実装済み・Rust 側・2026-09-13】

パッチアプリは127MB規模のasar全体を読み込む必要はない。asarはヘッダ（JSON、各
ファイルのオフセット・サイズを記述）＋ファイル本体の連結という単純な形式なので、
該当1ファイルの範囲だけシークして読めば済む。

✅ **既存クレートに頼らず自前実装：[patch_app/src/asar.rs](../../patch_app/src/asar.rs)。**
Chromium Pickle形式のヘッダを素の`serde_json`だけでパースする小さな実装（依存追加なし）。
win/macとも実機のapp.asar（127MB・133MB規模）で`@electron/asar`の`extract-file`と
バイト単位で一致することを検証済み（該当ファイルだけシークして読む設計目標も実測で確認）。
`unpacked: true`（asar外に展開されたファイル）は未対応（`setting.sn`は小さく通常
unpack対象にならない前提）。

sn_extension側：[genLegacyPatch.ts](../genLegacyPatch.ts)が`assertHasExperienceConst()`→
`encryptedChecksum()`→`settingSnFileName()`→`appendPatchFooter()`の順で処理し、
`patch_app`（Rust）が読み取れる形式で書き出す。TS側で生成したファイルをRust側の
`footer::extract_trailing_json()`/`parse_config()`で実際に読めることをクロス言語で
検証済み（往復整合性OK）。

## 詰められていない仕様【棚卸し・2026-09-12】

実装を先に進めたことで見えてきた、設計の前提に関わる事項の記録。項目1〜8は決着済み。

1. **複数の過去出荷ビルドに対応する必要がある**：`setting.sn`はゲームアップデートの
   たびに変わるため、チェックサム1個との一致だけでは過去バージョンの正規購入者を
   誤って弾いてしまう。[genLegacyPatch.ts](../genLegacyPatch.ts)は`legacyInstallers`
   （過去出荷ビルドのインストーラーファイルそのもの）を入力に取り、各ビルドから
   [extractSettingSnFromInstaller()](../InstallerExtract.ts)で`setting.sn`を抽出、
   チェックサム配列（`Config.checksumSetting`）に積む。鍵は`settingSnFileName`の算出
   （`uuidv5(relPath, pass)`）にのみ使い、平文にはアクセスしない。win`.exe`(NSIS)・
   mac`.dmg`双方とも実機データで動作検証済み（同一ビルドは同一チェックサムが得られ、
   体験版は異なるチェックサムになることを確認済み）。「インストール済みアプリを
   実機スキャンして自動収集」（`scanInstalled: true`）も`legacyInstallers`と併用可能
2. **体験版インストーラーの誤混入は自動検出できない**：`assertHasExperienceConst()`は
   `&const.体験版`の存在しか見ておらず、値の真偽までは見ていない。`crypto:true`の
   プロジェクトは平文にアクセスできず原理的に自動検出不可能なため、生成時に警告表示
   するのみとした（`crypto:false`のみ引き続き自動チェックし、失敗時は生成を中止する）
3. **`downloadUrl`が直接ファイルURLである保証が無い**：紹介ページを渡されると`curl`は
   HTMLを取得するだけでインストーラは手に入らない。
   [DownloadUrlCheck.ts](../DownloadUrlCheck.ts)が`Range: bytes=0-4095`で先頭4KBを
   取得し、Content-Type・マジックバイトで判定する（検証失敗時は警告のみで生成は続ける。
   実URLで動作確認済み）。`patch_gen_gui`のR2アップロード経由なら、PUT成功時点でURLの
   正しさが構造的に保証されるためこの検証は不要（外部で手動ホストしたURLを手入力する
   経路では引き続き有効）
4. `crypto:false`プロジェクトでの`settingSnFileName`は固定文字列`"setting.sn"`
   （`crypto:true`なら`uuidv5()`計算）で分岐するだけで解消し、フォルダ位置の算出は
   不要になった
5. **署名なし配布物への Gatekeeper／SmartScreen 警告は許容する**（作者確認）。コード署名
   （Apple Developer Program・Windows用証明書）は個人メーカー向けツールとして
   費用対効果が見合わないため導入しない。README等の配布時案内文で「警告が出ても
   問題ない」旨を説明する運用で対処する
6. **本家／分家・エンジン世代をまたいだasar構成の一致性**：basename探索方式に変更した
   ため、`out/renderer/prj/`配下の具体的な配置構造を知る必要が無くなった。実際に
   `sn_osk_gitayu`は`skynovel_esm`の`out/renderer/prj/`とは異なる`doc/crypto_prj/`
   という構成だったが、basename探索のおかげで実害は無かった
7. **⚠️ electron-builderの制約でwin環境の開発者はmac版パッチを作れない場合がある。**
   electron-builderはWindows上でmacOS向け（`.app`/`.dmg`/`.pkg`）をビルドできない
   （署名の有無に関わらない制約）。クロスビルドはmac→winの一方向のみで、win環境の
   開発者はそもそも自分のゲームのmac版をビルドできない可能性が高い。対処法は無い
   構造的制約として、利用者への説明文言でカバーする（残件#2）
8. **過去出荷ビルドに体験版チェック機構（`setting.sn`）自体が実装されていない場合が
   ある。** `sn_osk_gitayu`のv1.0.0（テンプレート更新前）では`setting.sn`・`trial.sn`
   がasar内に存在しなかった。[extractSettingSnFromInstaller()](../InstallerExtract.ts)
   が例外を投げるが、これはハードエラーにせず**②インストーラー本体丸ごとの
   チェックサム（`checksumInstaller`）へのフォールバックとして常に埋め込む**
   （`genLegacyPatch.ts`は警告を表示するのみで生成は止めない）。
   **この機構が無い古いビルドの購入者も②のフォールバックにより救済できる**
   （購入者に当時のインストーラー本体を選んでもらう一手間がかかる。
   [patch_app/src/main.rs](../../patch_app/src/main.rs)の`process_app()`参照）。
   唯一の制約は体験版混入の自動検証ができないこと（②では体験版・製品版の中身の
   違いを機械的に確認する手段がないため、開発者が目視で確認する必要がある）
9. ✅ **archを一切見ていない → macOS 27 Golden Gate（Rosetta終了予定）を受けて
   「バージョン更新」とは別の「arch移行」を届ける必要が生じた → 対応実装済み
   （2026-09-17判明・同日実装）**

   **発端**：macOS 27 "Golden Gate"が2026-09-14にリリース済み。Apple Silicon専用の
   初バージョンで、Intel Macはこれ以上OSアップデートできない。Rosetta 2
   （Intelアプリをarm64上で動かす変換層）はmacOS 27までが一般アプリ向けの
   フルサポートで、**macOS 28（来年想定）で一般用途のRosettaは終了**し、以降は
   「古い保守されていないゲームタイトル」向けの限定サポートのみが残る見込み
   （SKYNovel製アプリがその対象に入るかは不明・Appleの基準が示されていない）。
   （[MacRumors](https://www.macrumors.com/2026/06/10/macos-golden-gate-last-to-support-intel-apps/)、
   [OSXDaily](https://osxdaily.com/2026/08/11/psa-macos-27-golden-gate-is-last-to-support-rosetta-intel-apps/)）

   **このツールへの影響**：過去にmac版をx64専用でビルド・配布していたメーカーの
   購入者が、Apple Silicon機でRosetta終了後のOSにアップデートすると、そのx64版が
   **起動できなくなる**。つまり本ツールには「新バージョンを配る」だけでなく
   「同じバージョンのままarm64／universalビルドに乗り換えさせる」という新しい
   役割が生まれた。

   **しかし現状の実装は、まさにこのケースで壊れる**：「既に最新版がインストール
   済みならDLをスキップする」判定（[patch_app/src/main.rs:86](../../patch_app/src/main.rs#L86)、
   `checksum_latest == installed_hash`）は、`setting.sn`の中身（または
   インストーラー本体のサンプル）から作るチェックサムの一致だけを見ており、
   **archの情報を一切見ていない**。開発者がバージョン番号を変えずにx64ビルドから
   arm64／universalビルドへ差し替えて再配布すると、`setting.sn`の中身は
   ビルドarchと無関係なので変わらず、`checksumLatest`は旧x64版と完全に一致する。
   結果、旧x64版の購入者に対して**「既にお使いのバージョンは最新です」と誤判定され、
   永遠にDLがスキップされ続ける**（arm64／universal版へ案内する道が無い）。

   [patch_app/src/detect.rs](../../patch_app/src/detect.rs)（インストール済みアプリ検出）も
   OS判定のみでarchを一切見ていない（macは`/Applications/{appName}.app`固定1パス、
   winは`ProgramFiles`系3ディレクトリを見るだけ）。

   **実装した対応（2026-09-17）**：
   - `patch_app`側に「インストール済みバイナリのarch判定」を追加
     （[detect.rs](../../patch_app/src/detect.rs)の`detect_installed_arch()`。
     Windows: PEヘッダのMachineフィールド、mac: Mach-Oヘッダのcputype／
     fat headerでuniversal判定。レジストリ等には依存せずファイルのバイト列のみで
     完結させる、このモジュール全体の方針を踏襲）
   - 設定JSONに`latestArch`（配布予定の最新版のarch。空文字列＝未提供）を追加
     （[footer.rs](../../patch_app/src/footer.rs)の`AppConfig::latest_arch`、
     TS側は[LegacyAppCheck.ts](../LegacyAppCheck.ts)の
     `T_LEGACY_PATCH_APP_CONFIG::latestArch`）。値は
     [genLegacyPatch.ts](../genLegacyPatch.ts)の`extractArchFromArtifactName()`が
     `latestInstaller`のファイル名（electron-builderの既定artifactName規約
     `${name}-${version}-${arch}.${ext}`）から抽出する。抽出できなければ空文字列のまま
     ＝archチェックを行わない従来動作にフォールバックする
   - スキップ判定を「`checksumLatest`が一致し、**かつ**archも一致する場合のみ
     スキップ」に変更（[main.rs](../../patch_app/src/main.rs)の`process_app()`）。
     ただしarch判定は自動検出（①setting.sn抽出）が成功した場合にしか行えない
     （②購入者にインストーラー本体を選ばせるフォールバック時は、インストール済み
     アプリ本体のパス自体が手に入らないため）。archが判定できない場合は
     従来通りスキップを許可する保守的な設計にした（後方互換：`latestArch`を
     渡さなければ挙動は変わらない）
   - Rust側3件・TS側1件のユニットテストを追加、`cargo test`（43件）・
     `bun test test/LegacyAppCheck.test.ts`（20件）・`bun run chk:types`で確認済み

   **再発防止策：stub自体のuniversal2化を実装済み（2026-09-17）**。
   `patch_gen_gui`（GUI）が生成のたびに呼ぶ`rebuild_and_resolve_stubs`
   （[lib.rs](../../patch_gen_gui/src-tauri/src/lib.rs)の`build_mac_universal_stub()`）を、
   mac向けは`x86_64-apple-darwin`・`aarch64-apple-darwin`の両方をビルドして
   `lipo -create`で1バイナリに結合する方式に変更した。stub自体はこれでIntel Mac・
   Apple Siliconどちらでも同じ1本で動くため、「stubがどのarchで動くか」を
   今後気にする必要が無くなった（実機で`lipo -info`により`x86_64 arm64`の
   2アーキテクチャを含むことを確認済み）。

   ⚠️ **副産物として判明した罠**：cargoバイナリだけをrustup版
   （`~/.cargo/bin/cargo`）に切り替えても不十分だった。cargoが内部で呼ぶ
   `rustc`は`$PATH`解決に依存するため、Homebrew版rustcが先に来ていると
   結局そちらが使われ、sysrootに`aarch64-apple-darwin`向けのstd/coreが無く
   ビルドが失敗する。`RUSTC`環境変数で`~/.cargo/bin/rustc`を明示する必要が
   あった（詳細は[Rust 開発環境の準備状況](#rust-開発環境の準備状況調査済み2026-09-12)
   に追記済み。`lib.rs`の`rustc_bin()`で対応）。

   ⚠️ **ゲーム本体（開発者が配布する.dmg/.exe自体）のuniversal化は別リポジトリ
   （テンプレート）側の話で、sn_extensionからは直接手を出せない。** こちらは
   引き続き開発者側の判断・作業が必要（electron-builderの`mac.target`に
   `universal`を指定する等）。stub側のuniversal化とは独立した課題として残る。
   **未検討：universal一本化するか、x64/arm64を両方式提供するか（2026-09-17
   提起）。** electron-builderのuniversal機能（`@electron/universal`）は
   asar内のアセット（画像・音声・スクリプト等）を1つだけ共有し、Electron
   ランタイム（Chromium/Node.jsのネイティブバイナリ）だけをarchごとに持つ構成に
   なる。アセット部分は共通だが、Electronランタイム自体が100〜150MB程度の
   比重を持つため、単純な2倍にはならないものの1.5〜1.8倍程度になると推定される
   （未実測。実際の増加率はテンプレート側で実測が必要）。開発者への案内
   文言・推奨方式の要否は未検討

   **副次論点（win側のarch）→ ia32を対象外と明示する方針で決着（2026-09-17）**：
   electron-builderの既定は`artifactName: '${name}-${version}-${arch}.${ext}'`
   （[PrjSetting.ts:307](../PrjSetting.ts#L307)）で、win-x64／win-ia32の2種
   （mac側は上記でuniversal2化されたためこの論点から外れた）のビルド成果物が
   生まれ得る一方、GUI（`patch_gen_gui`）の「最新版インストーラー」欄はwin/macの
   2つしか無くarch軸が無い。ia32バイナリはWOW64で64bit機でも動くがx64はia32専用機で
   動かないという非対称性があるため、「安全な代替」を選ぶならia32側が候補になり
   得たが、**32bit専用のWindows実機は現在ほぼ流通しておらず、Linuxサポートを明示的に
   対象外とした過去の判断と同様の整理として、ia32は対象外と明示する運用に決定した**
   （作者確認・2026-09-17）。win側は事実上x64のみを想定する運用とし、GUIへの
   arch軸追加は行わない。`extractArchFromArtifactName()`のia32抽出ロジック自体は
   削除せず安全側の実装として残す（ia32ビルドの`latestInstaller`を誤って渡した場合も
   arch不一致でスキップを止める＝安全側に倒れるだけで、誤動作はしないため）。

### スコープの観察（2026-09-14・議論のみ）

`genUpdUrl.ts`（通常配布のupd_url.json生成）・`genLegacyPatch.ts`（過去アプリ向けパッチ生成）・
R2アップロード（未着手）は、どれも「開発者がリリース物を用意してホスティング先に届ける」という
同じ関心事の異なる断面であり、`patch_gen_gui`は将来的にこの3つを橋渡しする
「リリースパッケージ管理ツール」に育つ可能性がある。ただし現時点では名称・アーキテクチャの
作り直しは行わない（R2アップロードの技術検証がまだ・実装しながら仕様を詰めるこれまでの
やり方を踏襲）。**独立ツール（`patch_gen_gui`）側での先行着手・技術検証を優先しつつ、
拡張機能内蔵GUIへの将来統合は頭の片隅に置く**、という方針。

**未検討：`patch_gen_gui`＋`patch_app`のpublic独立リポジトリ化（2026-09-17提起）。**
規模・機能の独立性は既に単なるサブツールの域を超えつつある。障害になりうるのは
`patch_gen_gui`が実行時に`genLegacyPatch.ts`等のsn_extension側TSロジックを
サブプロセスで呼ぶ設計（`sn_extension_root()`で相対的にリポジトリを探す）で、
リポジトリを分けただけでは実行に引き続きsn_extensionのクローンが必要になる点
——ただし調査の結果、この依存は見た目ほど重くない。実行時に必要なのは
[genLegacyPatch.ts](../genLegacyPatch.ts)・[LegacyAppCheck.ts](../LegacyAppCheck.ts)・
[Encryptor.ts](../Encryptor.ts)・[InstallerExtract.ts](../InstallerExtract.ts)・
[DownloadUrlCheck.ts](../DownloadUrlCheck.ts)の計約900行のみで、外部依存も
`uuid`・`7zip-bin`・`@electron/asar`という軽量npmパッケージ3つだけ。
`CmnLib.ts`・`vscode`・LSPサーバー側への参照は全て`import type`（型情報のみ）で
実行時のJSには一切残らず、vscode拡張機能本体への実行時依存はゼロ。独立化するなら
この約900行＋テスト約370行をコピー同梱し、`sn_extension_root()`探索を廃止すれば
現実的に成立する。方向性自体は未定・保留中。

## 現状の結論

- **配布パッチアプリの拡張機能統合**（内蔵GUI提供・購入者チェック機構の本結線）は
  Marketplace 再申請の決着待ちで着手不可（残件#1）。実装基盤・判定ロジックの設計は
  既に固まっているため、着手可能になった時点ではその設計をそのまま結線するだけでよい。
- 一方、**パッチ生成ツール（試作単体アプリ）は拡張機能とは独立しており先行着手できる**
  （2026-09-14決定。[パッチ生成ツール（試作単体アプリ）](#パッチ生成ツール試作単体アプリ2026-09-14todomd-0-より移動)参照）。
  ✅ **CLIロジック（[genLegacyPatch.ts](../genLegacyPatch.ts)・[InstallerExtract.ts](../InstallerExtract.ts)・
  [DownloadUrlCheck.ts](../DownloadUrlCheck.ts)・[LegacyAppCheck.ts](../LegacyAppCheck.ts)の
  asar抽出関数）は実装・実機検証・結線まで済み（2026-09-14）。**
  `sn_osk_gitayu`の実配布物（win `.exe`・mac `.dmg`）で、同一ビルドから同一チェックサムが
  得られることまで確認した。downloadUrl検証・実機スキャンの両方も `genLegacyPatch.ts` に
  結線し、実行して動作確認済み。
  ✅ **GUI（[patch_gen_gui/](../../patch_gen_gui/)。Tauri v2）も実装・実地検証済み**
  （[GUI設計案](#gui設計案2026-09-14実装2026-09-17実地検証済み)参照。クリック操作の自動E2Eのみ未実施）。
  ⚠️ 副産物として、過去出荷ビルドに体験版チェック機構自体が無い場合があるという制約も
  判明した（[詰められていない仕様#8](#詰められていない仕様棚卸し2026-09-12)参照）。
  ✅ **`sn_kowloon`を使った実プロジェクトでの通し検証・Windows実機検証とも完了済み。**
  GUI操作→生成→生成物の実行→旧版検出→チェックサム一致→R2からの実ダウンロード完了、
  という一連の流れを人手で確認済み。win/mac双方のstubビルド・動作も実機検証済みで、
  技術的な残件はGUIクリック操作の自動E2E（優先度低）のみ。
- 「この方策ではない別のアイディア・既存webツール」は調査した範囲では見当たらなかった
  （`electron-updater`/Squirrel系は「動いているアプリ自身の自動更新」が前提で、更新機構が
  無い/壊れた過去アプリには効かない。Steam/itch.io等のランチャー配信は直接配布ゲームには
  適用不可。「旧正規購入者だけに新版を渡す」認証付きパッチという要件自体がニッチで、
  汎用OSSは見当たらない）。
